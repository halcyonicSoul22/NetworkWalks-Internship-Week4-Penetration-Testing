Section 01

Executive Summary

A black-box penetration test was conducted against https://medirozahospital.com, the web infrastructure of Mediroza General Hospital. The assessment revealed four significant vulnerabilities — two rated Critical and two rated High — that together allowed a simulated attacker to gain unauthorised access to confidential patient medical records, staff salary data, national identification numbers, and shareholder financial information, all without any prior credentials or insider knowledge.

The most severe finding was a SQL Injection vulnerability in the Patient Portal login page that allowed complete authentication bypass. This gave access to three encrypted confidential pathology lab reports. The encryption on these reports was subsequently cracked using widely available password-cracking tools due to the use of extremely weak passwords (123456, password). Additionally, an exposed database backup file was found publicly accessible on the web server, containing the full HR records of 30 employees and financial shareholder data.

The combination of these vulnerabilities represents a critical risk to patient confidentiality, staff privacy, and regulatory compliance under healthcare data protection legislation.

Findings and Proof of Exploitation

F-01 — SQL Injection: Authentication Bypass
Patient Portal Login  |  /patient/login.php
Critical
Vulnerability Type
SQL Injection (Authentication Bypass)
CVSS Score (Estimated)
9.8 — Critical
Affected Endpoint
POST /patient/login.php
Parameter
username (unsanitised)

Description

The Patient Portal login form at /patient/login.php was found to be vulnerable to SQL Injection. The username parameter is passed directly into a MySQL query without sanitisation or the use of prepared statements. By injecting a SQL comment sequence, it was possible to terminate the password-checking clause and log in as any user — or all users — without supplying a valid password.

Proof of Exploitation

The following cURL command was used to inject the payload and retrieve the authenticated dashboard:

# SQL Injection payload — comment sequence terminates password check
curl -s -X POST https://medirozahospital.com/patient/login.php \
  -d "username=admin'-- -&password=x" \
  -L -c cookies.txt -o dashboard.html

Injected SQL logic (inferred):

-- Original query (assumed):
SELECT * FROM users WHERE username = 'INPUT' AND password = '...'

-- After injection:
SELECT * FROM users WHERE username = 'admin'-- -' AND password = '...'
-- ↑ password check is commented out — login succeeds
✓ Evidence — Successful Access

The server returned HTTP 200 with the authenticated dashboard page titled "My Reports | Mediroza Patient Portal", listing three confidential pathology lab reports belonging to patients S. Dlamini (LR-2024-1187), P. Reddy (LR-2024-1192), and E. Thompson (LR-2024-1205).

⚠ Impact

An unauthenticated attacker can access any patient's confidential medical records without credentials. Three PDF pathology reports were downloaded and decrypted, exposing patient names, dates of birth, patient IDs, referring doctor names, and sensitive laboratory results.

F-04 — Verbose SQL Error Disclosure
Patient Portal  |  /patient/login.php
Medium

Description

When an invalid SQL payload was submitted to the login form, the server returned a raw MySQL error message directly in the HTTP response, revealing the underlying database query structure and MySQL version information.

Warning: mysqli_query(): You have an error in your SQL syntax; check the manual
that corresponds to your MySQL server version for the right syntax to use near
'' OR '1'='1' at line 1
⚠ Impact

Verbose error messages assist attackers in refining SQL injection payloads by revealing query structure, database type, and syntax expectations. This information directly aided the successful exploitation documented in F-01.

Section 05

Recommendations and Remediation

F-01 — SQL Injection (Critical Priority)

🔧 Recommended Actions
  • Use Prepared Statements / Parameterised Queries: Replace all dynamic SQL query construction with prepared statements using PDO or MySQLi. This is the most effective defence against SQL injection.
  • Input Validation: Validate and sanitise all user-supplied input on the server side before processing.
  • Implement a Web Application Firewall (WAF): A WAF can detect and block common SQL injection patterns as an additional layer of defence.
  • Principle of Least Privilege: The database account used by the web application should have only SELECT privileges — not full database access.
  • Code Review: Conduct a full code audit of all login and query-processing pages across both the patient and staff portals.

F-02 — Exposed Database Backup (Critical Priority)

🔧 Recommended Actions
  • Remove immediately: Delete or relocate the mediroza_db_backup_2019.sql file from the public web root immediately.
  • Store backups outside web root: Database backups must never be stored in publicly accessible directories. Use a secure, private location such as /var/backups/ outside of /public_html/.
  • Encrypt all backups: Apply strong encryption to all backup files at rest.
  • Audit all directories: Review the entire web root for other backup files, configuration files, or exported data.
  • Incident Response: Given the national ID and salary data exposed, consider notifying affected employees as required under POPIA.

F-03 — Weak PDF Passwords (High Priority)

🔧 Recommended Actions
  • Enforce strong password policy: Minimum 12 characters, combining uppercase, lowercase, numbers, and symbols. Never use common dictionary words.
  • Use randomly generated passwords: Generate passwords programmatically using a cryptographically secure random generator for each lab report.
  • Consider a patient portal delivery model: Instead of password-protected PDFs, deliver reports through the authenticated patient portal where access control is server-enforced.
  • Upgrade encryption standard: Use AES-256 PDF encryption rather than legacy RC4 128-bit.

F-04 — Verbose Error Disclosure (Medium Priority)

🔧 Recommended Actions
  • Disable display_errors in PHP: Set display_errors = Off in php.ini for the production environment.
  • Use generic error messages: Show only "Invalid username or password" — never reveal which field is incorrect or expose SQL syntax.
  • Log errors server-side: Errors should be logged securely on the server, not displayed to users.

F-05 — Directory Listing (Medium Priority)

🔧 Recommended Actions
  • Disable directory listing on LiteSpeed: Add Options -Indexes to the .htaccess file in all web directories, or configure this globally in the server settings.
  • Add index files: Ensure every directory has an index file to prevent directory listing from activating as a fallback.
  • Regular directory audits: Periodically review publicly accessible directories for any unintended file exposure.

Conclusion

This assessment identified a chain of critical vulnerabilities that, when combined, expose Mediroza General Hospital to significant risk of patient data breach, regulatory penalties, and reputational damage. The most urgent remediation actions are the removal of the exposed database backup file and the patching of the SQL injection vulnerability in the patient portal. It is strongly recommended that a follow-up penetration test be conducted after remediation to verify that all issues have been resolved effectively.
